> audits your Git rules, recommends what to install, and installs only what you pick and confirm.
> It tells you which tracked files the rules would now exclude and checks the result with Git itself.

# Version control

A Unity project is mostly generated files, and a few folders hold the project's real value. These two
files tell Git which is which, so a clone stays small, diffs stay readable, and nobody commits a
2 GB profiler capture by accident.

| I want to… | Give your agent |
|---|---|
| Set up Git rules for my Unity project | [SetupVersionControl.md](SetupVersionControl.md) |

Example prompts:

- *"Set up version control for my Unity project from this document."* Proposes the defaults for you to confirm.
- *"Review my current .gitignore and .gitattributes against this document, change nothing."*
- *"Set up the Git rules, but keep ThirdPartyAssets in the repository and don't use LFS."*

## What happens when you hand it over

1. **Audit.** The agent reads your existing `.gitignore`, `.gitattributes`, Git and LFS setup, and the
   two Unity settings Git depends on.
2. **Recommendations.** The ignore block, the attributes block, ThirdPartyAssets exclusion, LFS, and
   merge setup are each a numbered recommendation with the trade-off.
3. **You pick.** Take any subset, "all recommended", or none; for example, the ignore file without LFS.
4. **You confirm.** The agent restates the exact files and commands and waits for explicit user confirmation. Nothing is
   written before it.
5. **Apply and verify.** It installs the confirmed blocks and checks them with Git. Skipped items
   come back in the report as proposals.

## What is in the folder

| File | Install it as | What it does |
|---|---|---|
| [Unity.gitignore](Unity.gitignore) | `.gitignore` in the Unity project root | Keeps generated, machine-specific, and large regenerable files out of Git |
| [Unity.gitattributes](Unity.gitattributes) | `.gitattributes` in the repository root | Normalizes line endings and routes large binaries to Git LFS |

Each file is one clearly marked block. The agent installs or refreshes only that block, so your own
rules around it survive an update.

## What gets ignored, and why

| Ignored | Why |
|---|---|
| `Library/`, `Temp/`, `Obj/`, `Logs/`, `UserSettings/` | Rebuilt by Unity, or personal to one machine |
| `Builds/` and the `_BurstDebugInformation_DoNotShip` and `_BackUpThisFolder…` folders beside a player | Build output and symbols; publish them as artifacts, not source |
| `*.csproj`, `*.sln`, `.vs/`, `.idea/` | Generated by Unity for your IDE |
| **Profiling and diagnostic captures** | See below |
| **`Assets/ThirdPartyAssets/`** | See below |
| Addressables, Test Runner, and Visual Scripting output | Generated content |

Everything else is committed, including `ProjectSettings/`, `Packages/manifest.json`,
`Packages/packages-lock.json`, and **every `.meta` file**. A `.meta` file holds an asset's GUID, and a
missing one breaks every reference to it.

### Profiling captures

The Profiler writes `.data` files to a `ProfilerCaptures/` folder in the project by default, and the
Memory Profiler writes `.snap` files to `MemoryCaptures/`. They are large, tied to one machine and
build, and easy to regenerate. These rules ignore:

- `ProfilerCaptures/` and `MemoryCaptures/`
- `*.pdata` (Profile Analyzer), `*.snap` (Memory Profiler), `*.rdc` (RenderDoc), `*.diagsession`, `*.etl`

When a capture is worth sharing, such as a baseline for a regression, attach it to the issue or pull
request, or store it outside the repository. `.data` is ignored by folder, not by extension, because
the extension is too common; if you save captures elsewhere, add that folder to the block.

### ThirdPartyAssets

The [folder layout](../FolderStructure/README.md) puts vendor imports in `Assets/ThirdPartyAssets/`.
This starter keeps that folder out of Git, which keeps the repository small and your history free of
other people's code. The trade-off is real:

- **Every contributor re-imports** those assets from the Asset Store or their source after cloning.
- **A clean clone is incomplete**, and a CI runner cannot download Asset Store content. If CI must
  build the project, either keep the folder in Git or give CI another way to fetch the assets.
- **Private or modified vendor code is lost** if it lives only there. Put code you changed outside the folder.
- Anything installed through Package Manager is not affected: `Packages/manifest.json` records it.

If those costs outweigh the size, tell the agent to keep ThirdPartyAssets; it removes one marked section.

## Git LFS

Textures, models, audio, video, and source art such as PSD files are large and cannot be merged, so the
attributes file routes them to [Git LFS](https://git-lfs.com/). It is optional: the agent asks, and
removes one marked section if you decline. If you use it:

- Install Git LFS on every machine and CI runner **before** the first checkout, then run `git lfs install`.
- Files committed before LFS stay in history as ordinary blobs. `unity vcs git migrate-lfs` prints the
  command to rewrite them, which changes shared history, so do it once and with the whole team.
- Hosting quotas apply. Check your provider's LFS storage and bandwidth limits.

## Merging scenes and prefabs

Unity's UnityYAMLMerge merges scene and prefab files by object instead of by line. It is configured
**per clone**, because the merge driver in `.git/config` names the Editor on your machine. Each
contributor runs `unity vcs merge-setup` once; it writes the matching attributes and checks the tool
with a test merge. Without the Unity CLI, follow the
[Smart Merge manual page](https://docs.unity.com/en-us/engine/6000.7/manual/get-started/project-configuration/version-control/smart-merge).

## Settings that make this work

Two Unity settings decide whether Git can do its job, and both are Unity 6 defaults: **Asset
Serialization = Force Text** and **Version Control Mode = Visible Meta Files**. The
[project settings guide](../ProjectSettings/README.md) covers them, and `unity vcs doctor` reports both.

## Adopting this in a repository that already has history

The agent never rewrites anything on its own. It lists the tracked files the new rules exclude and
offers `git rm -r --cached <path>` for each group. That keeps the files on your disk but **deletes them
from teammates' folders when they pull**, so coordinate it, especially for vendor content.

## Pressure-tested, October 2026

- **Behavior, with real Git:** a throwaway repository received both files and was checked with
  `git check-ignore` and `git check-attr`: 38 paths ignored, 17 kept (every `.meta`,
  `ProjectSettings`, `Packages/manifest.json` and `packages-lock.json`, `.vscode/extensions.json`,
  nested folders named like the excluded ones), and 7 paths routed to LFS. Removing either optional
  section left a working file. The check runs as part of `AuditInstructions/Tools/validate_all.py`.
- **Against Unity's own checker:** on a Unity 6000.7.0b4 project, `unity vcs doctor` found no stale
  rules, no LFS pattern gaps, and no line-ending gap. Its single finding, `META_FILES_IGNORED`,
  appears only while the ignored ThirdPartyAssets `.meta` exists on the machine, so a clean clone or CI
  run does not trigger it. Starting from the previous root `.gitignore`
  it reported 16 template rules missing; this version includes them.
- **Merge setup:** `unity vcs merge-setup` was run in the same project and wrote its own block and
  driver without conflicting with this file.

Not tested: a clone of an existing large repository, Windows line-ending behavior, LFS against a real
remote, and the manual (no CLI) merge setup.
